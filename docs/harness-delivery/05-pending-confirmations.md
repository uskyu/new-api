## 待确认事项 1：usage 字段是否允许 `null`

### 网关当前实现

`usage` 对象的四个基础字段在网关侧实现为**可空**：

```json
{
  "input_tokens": null,
  "output_tokens": null,
  "cache_read_tokens": null,
  "cache_write_tokens": null,
  "total_tokens": 1000,
  "split_known": false
}
```

### 为什么需要 `null`

网关面临三种真实数据情况：

| 情况 | 网关掌握的信息 |
| --- | --- |
| 上游返回完整 usage | 输入、输出、缓存各自的实际值 |
| 上游只返回 total_tokens | 只知道总量，**不知道输入输出各多少** |
| 上游完全没返回 usage | 什么都没观测到 |

第二种情况若强行填 `0`，等于告诉 Harness「确认没有输入输出消耗」——这是**错误声明**。
`null` 才能如实表达"未测量"。

### 第四轮文档的表述

第四轮 §4.4 的字段表列出 `usage` 为 `input/output/cache read/cache write`，
**未说明是否允许 `null`**。

### 需要 Harness 确认

- [ ] 解析器能否接受 `null`？
- [ ] 若使用强类型（Go `int`、Java `int`、TS `number`），`null` 会反序列化失败。
      是否需要改用可空类型（`*int` / `Integer` / `number | null`）？

### 网关的备选方案

若 Harness 无法接受 `null`，可选：

1. **Harness 改用可空类型**（推荐）
2. 网关跳过无法拆分的 usage 事件，只在 `usage_source=unavailable` 时输出
3. 双方约定其他表达方式

## 待确认事项 2：新增字段 `total_tokens` 与 `split_known`

### 网关当前实现

网关在 `usage` 对象中额外输出两个字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `total_tokens` | `int \| null` | 上游报告的总量 |
| `split_known` | `bool` | 输入/输出是否分别观测到 |

### 为什么需要这两个字段

仅靠四个基础字段无法区分「total-only」和「完全无数据」：

```json
// total-only：有总量，无拆分
{"input_tokens": null, "output_tokens": null, "total_tokens": 1000, "split_known": false}

// 完全无数据：连总量都没有
{"input_tokens": null, "output_tokens": null, "total_tokens": null, "split_known": false}
```

没有 `total_tokens` 和 `split_known`，这两种情况在 JSON 上完全一样。

### 第四轮文档的表述

第四轮 §4.4 **未定义这两个字段**。

### 需要 Harness 确认

- [ ] 接受这两个新增字段？
- [ ] 还是要求网关改用其他表达方式？

### 兼容性说明

这两个字段是**纯新增**，不影响已有字段解析。若 Harness 忽略未知字段，可安全对接。

## 待确认事项 3：`refunded` 时 `total_amount` 可否非零

### 网关当前实现

退款时**保留**已发生的采购成本，`total_amount` **非零**：

```json
{
  "event_type": "refund",
  "status": "refunded",
  "billing": {
    "base_amount": "2.0000000000",
    "total_amount": "1.7600000000"
  }
}
```

### 为什么保留非零金额

网关只知道**客户**被退款，**不知道供应商是否退款**。

真实情况：供应商对已完成生成但任务失败/超时的请求**仍然收费**。若网关把采购成本
归零，等于声称供应商也没收费——这是网关无法确认的事实。

而对账的目的正是发现这类差异。归零会掩盖它。

### 第四轮文档的表述

第四轮 §4.3 的退款样例金额为 `0`，容易被理解为「退款即归零」。
文档未明确说明退款时采购成本应如何表达。

### 需要 Harness 确认

- [ ] 接受「`refunded` ⇒ `total_amount` 可非零」？
- [ ] 还是要求 `refunded` 时金额必须为 `0`？

### 若 Harness 要求归零

网关需要新增一个字段区分「客户已退款」与「供应商成本已撤销」。这会扩大契约范围，
需要双方另行设计——**不建议**在本期仓促决定。

### 唯一例外

用量计价任务在**数量从未获知**时退款，金额为 `0`，且对应 B1 事件的
`usage_source` 为 `unavailable`，明确说明"数量未观测"。

## 待确认事项 4：缺失关联头的策略（已定案）

### 结论

**采用方案 A：拒绝请求。** 自 2026-10-29 起网关已实施：

```
HTTP 400 REQUEST_INVALID
"X-Harness-Request-Id is required"
```

`X-Harness-Run-Id` 同理，缺失时消息为 `X-Harness-Run-Id is required`。
拒绝发生在转发上游之前，因此**不产生费用，也不产生账本事件**。

### 为什么选择拒绝

账本的价值在于完整性。无关联 ID 的请求进入系统后，后续无论怎么查都无法对应，
只能人工排查；而这类请求仍然会被计费，等于制造了一笔无法对账的成本。

### 对 Harness 的要求

- [ ] 所有模型调用（A1/A2/A4/A9）都必须同时携带两个关联头
- [ ] 两个值都 ≤64 字符，字符集 `A-Z a-z 0-9 - _`

## 本轮新增的硬性要求（网关已实施）

以下不是待确认项，而是当前网关的确定行为，需在对接时遵守：

| 项 | 行为 |
| --- | --- |
| `X-Harness-Run-Id` | **必填**，≤64 字符。会写入每条 B1/B3 账本行，并在 B1 事件中返回 |
| `X-Harness-Request-Id` | 必填，≤64 字符。账本主键，B1/B3 均按它查询 |
| `X-Route-Group` | 可选，值为 A3 的池 id。不传走默认池；传未知池返回 403 |
| `model` 字段 | 必须填 A3 `models[]` 中的真实模型 id，不是池 id |

## 已确认事项（供对照）

以下两项此前的判断已核实，**不需要** Harness 再次确认：

### `observed_at` 格式

网关统一使用 RFC3339 UTC **三位毫秒**：`2026-10-25T11:20:37.068Z`

第四轮文档 §4.2 用带毫秒格式、§4.3 用不带毫秒格式，属文档内部不一致。
网关统一带毫秒，符合 RFC3339 且更精确。

**无需确认**——这是合法的 RFC3339 格式。

### `usage_unit` 本期只有 `token`

第四轮列出 `token` / `image` / `audio_second` / `character` / `request` / `other`
是为未来定义可选值，不代表本期必须全部产生。

本期只做模型 Token 计费，实际只会产生 `token`。

**无需确认**——符合本期业务边界。
